For each of the seven subsystems: an illustrated UML use case diagram showing actors, sub-modules, and use cases, followed by the runtime business activity narrative.

Subsystem 01

Room Operations

Public room listings & inquiries, GM room inventory CRUD, public room type cards, occupancy dashboard, inquiry email replies, and system-automated GM notifications + audit trail.

Use Case Diagram

Fig. 1.1 — Room Operations use cases (Public Visitor Flow, GM Room Management, GM Inquiry Management, System Automated).

Business Activity
  • Edit Room (Amenities & Description) — The GM edits room number, floor, type, rate, max occupants, status, description, and amenities from the Edit modal. Photos are no longer managed per-room — the public-facing photos live on the Public Room Type Cards instead, which is the only place the GM uploads images. The System writes room_updated to the audit log and stamps last_updated_by + last_status_update.
  • Edit Public Room Type Cards — The GM opens the Public Cards editor and edits the two cards rendered on the landing page: title (max 60), subtitle, price, max occupants, amenity rows (icon picked from the FontAwesome catalog + label), and photo slots. Inline image upload validates mime (jpg/jpeg/png/webp) and size (≤2 MB), stores under storage/app/public/room-type-cards/, and writes the public URL into the photos slot. On save, all rules are validated, the JSON is persisted to system_settings.room_type_cards, and room_cards_updated is audit-logged.
  • View Room Listings — Once the inventory and cards are in place, the Public Visitor opens the public landing page (no login required) and sees two Room Type Cards (Compact / Spacious) rendered with photos, subtitle, max occupants, amenity chips with FontAwesome icons, base price, and a live available count queried per type from the rooms table where status = available.
  • View Room Type Detail — The Public Visitor can drill into a per-type detail page (/rooms/{compact|spacious}) showing every room of that type ordered by floor and room number, with combined photo gallery, deduplicated amenities list, available count, and rate range (min–max).
  • Submit Room Inquiry — The Public Visitor fills the inquiry form (sender_name max 100, contact_number max 20, optional email, message max 500). The "Inquire about Compact/Spacious" buttons pre-select the preferred room type and scroll to the form. On submit, the System creates an Inquiry row, fans out a bell notification to every active GM, and shows a thank-you confirmation.
  • Notify GMs on New Inquiry — The System writes a NotificationLog row of type new_inquiry for every active GM the moment the public form is submitted, so the bell badge increments without polling.
  • View & Filter Inquiry Log — The GM opens the Inquiry Log (15/page) showing every inquiry latest-first with sender info, preferred type, message, and status. Status filter drops to Open / Responded / Closed.
  • Send Email Reply to Inquiry — The GM opens the Compose panel for an inquiry that has an email on file (otherwise blocked). Subject (required, max 150) is pre-filled to "Re: Your room inquiry…" and body (max 3000) starts with a greeting template. On Send, the System dispatches InquiryReplyMail, marks the inquiry Responded, stores the body in gm_notes, and stamps responded_by + responded_at.
  • Mark Inquiry Responded — Alternatively the GM may manually mark an inquiry Responded without sending an in-app email (e.g., when the reply happened by phone), stamping responded_by and responded_at.
  • Close Inquiry — The GM closes a finished inquiry; the System sets its status to Closed so it drops out of the default Open view. (If the inquiry leads to a lease, the flow continues into SS4 Contract Management.)
  • Update Room Status (locked while occupied) — Throughout a tenancy the GM changes a room's status (available / occupied / under_maintenance) directly from the room row. While a tenant is occupying the room (current_tenant_id is set) the dropdown is locked — maintenance on an occupied room is handled in-place via a Tenant Request (SS7), not by flipping the room's status. Once the room is empty, the GM may switch to any state and the System automatically clears current_tenant_id; every change is stamped and audit-logged as room_status_change.
  • View, Search & Filter Rooms — The GM opens the Room Manager any time to monitor inventory: a paginated list (20/page) sorted by floor + room number, search box for room number, and dropdowns filtering by floor (1/2/3) and status (Available / Occupied / Under Maintenance).
  • View Occupancy Dashboard — The GM opens /admin/dashboard at any time and sees totals (rooms, available, occupied, under maintenance), the full room list with current tenant + floor, expiring contracts (≤30 days), revenue-by-month chart, and a bill-status doughnut.
  • Archive Room (Clear Tenancy) — Clicking Archive on a room now ends the current tenancy without removing the room from inventory. With a confirmation prompt, the System: (1) snapshots the room's current state into archives (record_type = room, source_subsystem = SS1); (2) if a tenant is occupying the room, archives the tenant account (record_type = tenant_account, source_subsystem = SS2) and flips the user to Archived; (3) terminates and archives any active contract on that room (record_type = contract, source_subsystem = SS4, scan path preserved); (4) resets the room itself — clears current_tenant_id, sets status = available, stamps last_status_update. The room row stays in inventory with its original number, floor, type, and rate intact — it can be edited and re-occupied immediately. Audit log entry: room_cleared. To remove a room entirely from the database, use Permanently Delete Room instead.
  • Permanently Delete Room — Finally the GM may permanently delete a room via a stronger confirm prompt. The System performs a forceDelete — the action is irreversible and is recorded as room_deleted in the audit log.
  • Audit-Log Room Events — Cross-cutting at every step, the System writes an AuditLog entry tagged source = SS1 for every room-affecting event: room_updated, room_status_change, room_archived, room_deleted, and room_cards_updated — capturing actor, role, timestamp, and a human-readable note for traceability and BBT verification.
Subsystem 02

Tenant Management

Tenant list, search & filter, account creation, manual archive & permanent deletion, tenant self-profile, first-login activation, and system-automated email / bell / audit / SS4 auto-archive.

Use Case Diagram

Fig. 2.1 — Tenant Management use cases (GM Account Management, Tenant Self-Service, System Automated).

Business Activity
  • Create Tenant Account — Starts after the contract is physically signed in SS4. The General Manager opens the Create modal and enters the tenant's full name and email. The System validates that the email is well-formed and unique, generates a random 10-character temporary password, hashes it for storage, sets the new account to Pending Activation with must_change_password = true, and dispatches the temp-password email. The form can also be cancelled, which closes the modal without persisting anything.
  • Send Temporary Password Email — Immediately after Create Tenant Account succeeds, the System sends the TempPasswordMail to the tenant's address containing the plain-text temp password and login instructions. The plain-text password is never persisted — only the hash is stored.
  • Activate Account (First-Login OTP) — Receiving the email, the Tenant logs in for the first time using the temporary password. The System (via SS6) sends a One-Time Password to the tenant's email. On correct OTP entry the account flips from Pending Activation to Active and the tenant is forced to set a new password before any portal screen renders.
  • View Tenant Dashboard — Once active, the Tenant opens /tenant/dashboard and sees a cross-subsystem snapshot: their active contract + room (from SS4), their latest bill with unpaid-count badge (from SS3), their recorded initial payment receipt, and the 5 latest notifications (from SS7). It is the tenant's home screen after every successful login.
  • View Own Profile — Once active, the Tenant opens the My Profile page and sees their full name, email, contact number, address, and emergency contact pre-filled from their account record.
  • Update Own Profile — The Tenant edits their own full name, contact number, address, or emergency contact and submits. The System validates the inputs (full_name required & max 100; contact_number max 20; address max 255; emergency_contact max 100), persists the changes, and shows a success flash. Email is read-only on this form.
  • Notify GMs on Profile Update — When a tenant saves their profile, the System writes a self-confirmation bell entry for the tenant and dispatches a bell notification to every active GM ("{tenant} updated their profile."), so the GM-side stays in sync without polling.
  • View & Search Tenant List — The GM monitors tenants any time from the Tenant Manager — a paginated list (15/page) showing full name, email, status, and action buttons, with a debounced live search by name or email.
  • Filter Tenants by Status — The GM filters the same list by account status: Pending Activation, Active, or Archived. The filter combines with the search term and re-paginates the result.
  • Auto-Archive on Contract End — When the lease ends, the contracts:auto-archive scheduled command finds the expired contract and the System auto-archives the linked tenant account: status flips to Archived, an Archive row is created (record_type = tenant_account, reason = "Contract expired — auto-archived"), and the room is freed back to Available. Termination from SS4 also triggers this archive flow.
  • Archive Tenant Account — Alternatively the GM manually archives a tenant from the list (with a confirmation prompt). The System copies the user record into the archives table (record_type = tenant_account, source_subsystem = SS2) and flips the user's status to Archived with archived_at and archived_by stamped.
  • Permanently Delete Tenant Account — Finally, the GM may permanently delete a tenant via a stronger confirmation prompt ("PERMANENTLY delete this tenant? This cannot be undone"). The System performs a forceDelete on the row — the action is irreversible and is recorded in the SS6 audit trail.
  • Audit-Log Tenant Events — Cross-cutting at every step, the System writes an AuditLog entry tagged source = SS2 for every tenant-affecting event: tenant_created, tenant_archived, tenant_deleted, and profile_updated — capturing actor ID, role, timestamp, and a human-readable note for traceability and BBT verification.
Subsystem 03

Billing & Collections

Tenant bill viewing, GM-driven initial-payment recording & monthly bill generation, payment confirmation, penalty overrides, lease-end archive, and the daily cron that drives grace reminders and penalty escalation.

Use Case Diagram

Fig. 3.1 — Billing & Collections use cases (Tenant Billing View, GM Billing Operations, daily-cron System Automated).

Business Activity
  • Record Initial Payment — Billing begins on move-in: the GM opens the Initial Payment modal and picks a contract from those in draft or active status with no initial payment yet. Selecting a contract auto-fills the deposit, first-month rent, and room-key fee from SS4 and pre-loads the contract's requested amenities (each with name + fee, editable add/remove rows). The System validates the date and payment method (cash / bank_transfer / e_wallet), refuses duplicates, computes total = deposit + first rent + key fee + amenities total, persists to initial_payments, and writes initial_payment_recorded to the audit log.
  • View Bills & Initial Payment Receipt — Once recorded, the Tenant opens My Bills and sees their initial-payment receipt plus every monthly bill issued latest-first (period, base rent, utilities, penalty, total, due date, status, paid_at). Note: the system does not accept online payments — payments are made offline and recorded by the GM.
  • Generate Monthly Bill — Each month the GM opens the Generate Bill modal, selects an active contract, and enters this month's electricity, water, and wifi charges. The System validates, computes utilities = electricity + water + wifi, total = contract base_rent_rate + utilities, writes a Bill row for period YYYY-MM due at end-of-month, and audit-logs bill_generated.
  • View, Search, Sort & Filter Bills — The GM monitors collections from the Billing Manager — every bill paginated 15/page, joined with tenant name, with a search by tenant name, a status dropdown (Unpaid / Grace / Overdue / Delinquent / Eviction / Paid / Archived), and column headers that toggle ascending/descending sort.
  • Apply Grace Period & Send Reminder (Days 1–3) — If the due date passes unpaid, the daily cron billing:apply-penalties picks every bill with status in {unpaid, grace, overdue, delinquent} whose due date is in the past, computes days_overdue, and during the grace window (configurable per contract via penalty_grace_days, default 3) sets status = Grace and dispatches a grace_reminder bell on day 1 and the final grace day. No penalty is applied yet.
  • Apply Daily Penalty & Mark Overdue (Day 4–13) — Once days_overdue exceeds the grace days but is below the delinquent threshold (config citiescapes.penalty.delinquent_day, default 14), the System computes penalty_amount = penalty_rate × (daysOverdue − graceDays), updates total = base_rent + utilities + penalty, and sets status = Overdue.
  • Escalate to Delinquent (Day 14) — When days_overdue reaches the delinquent threshold (default 14) and is below the eviction threshold (default 30), the System recomputes the penalty, sets status = Delinquent, and on the threshold day exactly dispatches a delinquent_notice bell.
  • Escalate to Eviction (Day 30) — When days_overdue hits the eviction threshold (default 30, configurable), the System recomputes the penalty, sets status = Eviction, and on the threshold day exactly dispatches an eviction_notice bell flagging that proceedings may begin.
  • Override / Waive Penalty — At any escalation stage the GM may override the penalty on a bill via the Override modal — a non-negative new amount and a written reason (max 500) are required. The System writes a PenaltyOverride row capturing original vs adjusted amount and reason, recomputes total = base_rent + utilities + new penalty, and audit-logs penalty_override with the before/after.
  • Confirm Payment (partial-payment aware) — The GM opens the Confirm Payment modal for an unpaid bill, enters amount + method (cash / bank transfer / e-wallet) + optional reference. The System writes a payments row, then recomputes the bill's outstanding balance (Bill::balance = total_amount − sum(payments)). Only when the balance reaches zero does the bill flip to paid; otherwise the existing status (eviction / delinquent / overdue / unpaid) is preserved and the action is audit-logged as payment_partial with the remaining balance. This prevents the prior bug where a partial payment falsely cleared the bill.
  • Request Payment Plan (Tenant) — A tenant whose bill is in delinquent or eviction sees a red banner on My Bills. Clicking Request payment plan creates a Tenant Request (SS7) with an auto-filled subject "Payment difficulty — Bill #N (period)" and a body summarising the balance. The System guards against duplicates (one open arrears request per bill), notifies every active GM via bell + email, and audit-logs payment_plan_requested.
  • Apply Deposit to Arrears (GM) — On a bill in delinquent or eviction the GM clicks Apply Deposit. The System computes the deposit credit remaining (contracts.deposit − contracts.deposit_applied_amount), applies the smaller of (deposit remaining) or (bill balance), creates a payments row tagged deposit_applied, increments deposit_applied_amount, and stamps deposit_applied_at so the same deposit cannot be applied twice. If the credit clears the balance the bill flips to paid. Audit-logged as deposit_applied_to_bill.
  • Mark for Termination (GM eviction shortcut) — If the tenant cannot or will not pay, the GM clicks Mark for Termination on the bill (with a strong confirm prompt). The System auto-fills a termination reason citing the bill, flips the linked contract to terminated, archives it to SS5 with the same reason, archives the tenant (SS2), and frees the room (SS1) — all in one call. Audit-logged as contract_terminated_arrears under SS3.
  • Audit-Log Billing Events — Cross-cutting at every step, the System writes an AuditLog entry tagged source = SS3 for every billing event: bill_generated, initial_payment_recorded, payment_confirmed, and penalty_override — capturing actor, role, timestamp, and a human-readable note for traceability and BBT verification.
Subsystem 04

Contract & Lease Management

Contract draft + amenity catalog, scan upload, manual activation, renewal & termination, two-step tenant acknowledgement, scheduled expiry warnings (30/7-day), and auto-archive + room/contract sync crons.

Use Case Diagram

Fig. 4.1 — Contract & Lease Management use cases (GM Contract Lifecycle, Tenant Acknowledgement, System Automated cron).

Business Activity
  • Create Contract Draft — After an SS1 inquiry is confirmed, the GM opens the Create modal and selects a tenant + room (the room's rate auto-fills base_rent_rate), then enters deposit, room key fee (default ₱200), start & end dates, penalty rate, grace days (default 3), and house rules. Amenities are added from a fixed catalog (Air Conditioner, Extra Mattress, Extra Double Deck Frame, Aircon Remote, Extra Key, Extra Pillow) — picking the name auto-fills its default fee. The PDF/image scan can be uploaded now or later. The System validates the inputs, persists with status = Draft, and writes contract_created to the audit log.
  • Edit Contract Draft — Before activation the GM may revise any field on the draft. The System validates and overwrites, replacing the scan path if a new file is uploaded, and audit-logs contract_updated.
  • View Scanned Contract (GM) — Once a scan is uploaded the GM can open the scan viewer modal for any contract and the file is rendered inline (PDF or image) or downloaded (DOC / DOCX) without leaving the Contract Manager. Scan upload now accepts .pdf, .jpg, .jpeg, .png, .webp, .doc, .docx up to 10 MB.
  • Request Scan Access (Tenant) — On My Contract the scan viewer is locked behind an approval gate. The Tenant clicks Request access; the System sets scan_view_status = pending, stamps scan_view_requested_at, and audit-logs contract_scan_view_requested.
  • Approve / Deny Scan Access (GM) — The GM sees a "Tenant requested access" badge on the Contracts page. Approve opens a confirmation (with optional note); Deny requires a reason that the tenant will see. The System stamps scan_view_decided_at and scan_view_decided_by, stores the note, and audit-logs contract_scan_view_approved or contract_scan_view_denied.
  • Revoke Scan Access (GM) — After approval the GM may revoke at any time; the System clears scan_view_status, audit-logs contract_scan_view_revoked, and the tenant's viewer returns to the locked state.
  • View Approved Scanned Contract (Tenant) — Once approved, the Tenant sees the scan inline on My Contract — PDFs in an iframe, images via <img>, Word files as a download button. If denied, the viewer shows the reason and a Request again button.
  • View Contract Summary — The Tenant logs in (via SS6 first-login OTP from SS2) and opens My Contract, seeing their current draft or active contract — room, dates, base rent, deposit, key fee, penalty terms, house rules, and a link to the scanned signed file when present.
  • Ack Step 1 — Terms Read — The Tenant clicks "I have read and understood the terms". The System stamps step1_acknowledged_at, writes contract_step1_ack to the audit log, and unlocks Step 2. Step 2 is blocked until Step 1 is recorded.
  • Ack Step 2 — Penalty Accepted (Activates) — The Tenant clicks "I accept the penalty clause". The System stamps step2_acknowledged_at, flips the contract to Active, stamps activated_at, links the room's current_tenant_id to the tenant, audit-logs contract_step2_ack, and the lease cycle begins (which in turn unlocks SS3 monthly billing).
  • Activate Contract — Alternatively, the GM may activate a draft directly from the Contract Manager (e.g., for paper-only signings). The System flips the contract to Active, marks the linked room Occupied with current_tenant_id, stamps the room update fields, and audit-logs contract_activated.
  • Sync Room–Contract Status — While leases are active, the cron room:sync-status reconciles the rooms table with active contracts: rooms with an active contract that aren't Occupied are flipped to Occupied with the right current_tenant_id; with the optional --cleanup flag, occupied rooms with no active contract are flipped back to Available — guaranteeing data integrity between SS1 and SS4.
  • View, Search & Filter Contracts — The GM monitors leases at any time from the Contract Manager — paginated 15/page latest first, search by tenant name, and a status dropdown for Draft / Active / Expired / Terminated.
  • Send 30-Day Expiry Warning — As a lease nears its end, the cron contracts:send-warnings finds every active contract whose end_date is in (now + 7 days, now + 30 days] and whose warning_30_sent flag is false, dispatches a 30-day bell to the tenant and every active GM, then sets warning_30_sent = true so the warning is never duplicated.
  • Send 7-Day Expiry Warning — The same cron then finds every active contract whose end_date is in (now, now + 7 days] and whose warning_7_sent flag is false, dispatches an URGENT 7-day bell to the tenant and every active GM, then sets warning_7_sent = true.
  • Renew Contract — Before expiry the GM may renew an existing contract. The System archives the old contract (record_type = contract, source_subsystem = SS4, reason = "Renewed — old contract archived", scan path preserved), marks it Expired, and pre-fills a new draft inheriting tenant, room, rent, deposit, key fee, amenities, penalty terms, and house rules — with start = old end + 1 day and end = old end + 1 year.
  • Terminate Contract — Alternatively the GM may terminate a contract early via the Terminate modal — a written reason is mandatory (max 500). The System sets status = Terminated with terminated_at + reason, archives the contract record (and its scan) to SS5, archives the tenant account (SS2) if still active, frees the room back to Available, and audit-logs contract_terminated. Note that SS3 also offers a Mark for Termination shortcut on eviction-status bills which calls the same logic with an auto-filled reason.
  • Auto-Archive Expired Contract — If neither renewed nor terminated, the cron contracts:auto-archive picks every active contract whose end_date has passed, sets status = Expired, archives the contract (and scan) into SS5 with archived_by = null (system), auto-archives the tenant account (SS2) if still active, and frees the room back to Available.
  • Audit-Log Contract Events — Cross-cutting at every step, the System writes an AuditLog entry tagged source = SS4 for every contract event: contract_created, contract_updated, contract_activated, contract_terminated, contract_step1_ack, and contract_step2_ack — for traceability and BBT verification.
Subsystem 05

Report and Archive Management

Always-on archive store fed by SS1–SS4 lifecycle events; GM-side filtered browser with tenant-account restore, permanent-delete, CSV export of the filtered list, and per-archived-contract PDF report — plus a complete audit trail of every archive action and export.

Use Case Diagram

Fig. 5.1 — Report & Archive Management use cases (GM Archive Browser, GM Export & Reports, System Automated archival + audit).

Business Activity
  • Auto-Archive from Rooms, Tenants, Billing & Contracts — SS5 is always on and is the first step in its own lifecycle: records flow in automatically whenever any other subsystem flags one for archival — SS1 archives rooms (record_type = room), SS2 archives tenant accounts (tenant_account, both manually and via the SS4 expiry cron), SS3 archives bills on lease end (payment), and SS4 archives contracts (contract) on renewal, termination, or auto-archive — preserving the scan path. Each row stamps source_subsystem, archive_reason, the originating record's full payload, and archived_by (GM ID or null for system).
  • View, Filter & Date-Range Archive — Once records are in the archive, the GM opens the Archive screen and sees every archived (non-restored) record latest-first, paginated 15/page. Filters narrow the list by record_type (room, tenant_account, contract, payment), by source_subsystem (SS1–SS4), and by an inclusive date range (From / To) on the archive's created_at. Each archived contract row exposes a link to its preserved scan path.
  • Export Archive to CSV — From the same Archive screen the GM clicks Export CSV. The System applies the current filters, streams a UTF-8 CSV (with BOM so Excel opens cleanly) containing Archive ID, Original ID, Record Type, Source Subsystem, Reason, Has Scan, Archived By, and Archived At — and audit-logs archive_exported_csv.
  • (Removed — Export Archive to Excel) — The .xlsx exporter and the PhpSpreadsheet dependency were removed because CSV satisfies the same use case (Excel opens UTF-8 CSV files natively and reliably). The Export CSV button above is now the single export path for the archive list.
  • Export Archived Contract to PDF — For any row whose record_type is contract, the GM clicks the PDF button. The System renders a printable A4 PDF via DomPDF including the contract data payload (tenant ID, room ID, dates, base rent, deposit, key fee, penalty terms, acknowledgement timestamps, requested amenities, house rules) and a reference to the preserved scan file path / URL — and audit-logs archive_contract_pdf. Useful for legal filing.
  • Restore Archived Tenant Account — Restore is scoped to tenant_account archives only — the one record type where restoration is both impactful and safe. The GM clicks Restore on a tenant-account archive row; the System re-activates the underlying user (status = Active, clears archived_at & archived_by) so the tenant can log in again, sets restored = true with restored_at = now, and audit-logs record_restored tagged SS5. Room, contract, and payment archives are immutable historical snapshots — they cannot be restored (un-terminating a contract or reviving a settled bill would collide with room occupancy and the penalty scheduler), so no Restore button is shown for those rows and the controller rejects any such attempt. To bring back a contract scenario, the GM creates a fresh contract draft (SS4) pre-filled from the archived data, which routes through the normal activation guards.
  • Permanently Delete Archive Record — When a record is no longer needed, the GM may permanently delete it. The System writes record_permanently_deleted to the audit log before deletion (so the trace survives), then removes the row. The action is irreversible.
  • Audit-Log Restore, Delete & Exports — Cross-cutting at every step, the System writes an AuditLog entry tagged source = SS5 for every SS5 action: record_restored, record_permanently_deleted, archive_exported_csv, and archive_contract_pdf — capturing actor, role, timestamp, the affected record type + ID, and (for exports) the row count, for traceability and BBT verification. (archive_exported_xlsx was removed alongside the XLSX exporter; CSV covers the same use case.)
Subsystem 06

User Access and Authentication

First-time activation via emailed OTP, ongoing email/password login, forced & voluntary password change, lockout after N failed attempts with auto-unlock, archived-account block, GM audit log + system settings, and the system audit trail.

Use Case Diagram

Fig. 6.1 — User Access & Authentication use cases (First-Time Activation, Ongoing Login & Password, Security & Lockout, GM Administration, System Automated).

Business Activity
  • First Login with Temporary Password — Right after the GM creates a tenant account in SS2, the temp password is emailed. The Tenant enters their email + temp password on the login screen. The System validates them, audit-logs login, and because the account status is pending_activation, immediately generates a 6-digit OTP (Hash::make stored, expiry from citiescapes.auth.otp_expiry_minutes, default 10), dispatches OtpMail, and redirects to the OTP screen.
  • Verify OTP & Activate — The Tenant enters the 6-digit OTP. The System validates it (digits:6), looks up the latest unused, unexpired record for the user, hash-checks the entered code, marks the OTP used, flips the user to Active with activated_at = now, audit-logs account_activated, and redirects to the password-change screen.
  • Resend OTP — If the OTP expired or never arrived, the Tenant can click Resend on the OTP screen. The System generates a fresh 6-digit code, stores its hash with a new expiry, and re-dispatches OtpMail.
  • Force First-Time Password Change — Immediately after activation, because must_change_password is true, the System redirects the tenant to Change Password after every successful login until they set their own password.
  • Login (Email & Password) — From here on, both the Tenant and the General Manager log in with email + password (≥6 chars). The System validates, calls autoUnlockIfExpired(), refuses locked / archived accounts with explicit messages, hash-checks the password, on success resets failed_login_attempts, opens a remembered session, stamps last_login_at, audit-logs login, and redirects role-aware (admin.dashboard for GM, tenant.dashboard for tenant).
  • Auto-Unlock if Lockout Expired — As a precondition on every login attempt the System calls autoUnlockIfExpired() on the user — if the account is locked but locked_until has passed, status flips back to Active, locked_until is cleared, and failed_login_attempts resets to 0.
  • Block Login if Account Archived — Also as a precondition: if the user's status is archived (set by SS2 manual archive or the SS4 expiry cron), the System refuses the login with the message "Account archived. Contact the General Manager." and never opens a session.
  • Lock After 5 Failed Attempts — On every failed password check the System calls incrementFailedLogin(), audit-logs failed_login with the attempt count, and once attempts reach the threshold (config lockout_threshold, default 5) sets status = locked with locked_until = now + lockout_minutes (default 15) — both values are configurable in System Settings.
  • Notify GMs on Lockout — The moment a lockout is applied, the System writes a NotificationLog row of type account_locked for every active GM (bell badge), so administrators can see the event without polling logs.
  • Change Password (Anytime) — Later in the lifecycle, voluntarily, the Tenant or GM submits current password + new password (min 8, confirmed). The System hash-checks the current password, hashes & saves the new one, clears must_change_password, audit-logs password_change, and redirects role-aware to the dashboard.
  • Logout — The Tenant or GM ends their session by POSTing to /logout. The System audit-logs logout tagged SS6 (capturing actor + IP), calls auth()->logout(), invalidates the session, regenerates the CSRF token, and redirects to /login. This is the only mutating route guaranteed to write an audit row even for guest-side request quirks.
  • Activated-Account Gate (Middleware) — The activated middleware runs before every authenticated route. The System reads the user's status and: (1) auto-unlocks if the lockout window expired (UC 6.6); (2) if status is locked, logs the user out and redirects to /login with a temporary-lock flash; (3) if status is archived, logs out and redirects with the archived-account flash; (4) if status is pending_activation, redirects to /otp/verify; (5) if must_change_password is true and the user is not already on the password-change route, redirects to /password/change. Only after all gates pass does the request continue to the controller/Livewire component. This guarantees every other use case starts from a known-good account state.
  • View, Filter & Search Audit Log — Throughout operations the GM opens the Audit Log viewer (paginated 25/page, latest first). Filters narrow by action (drawn from distinct values in the table) and subsystem (SS1–SS7). A search box runs against the action's details and the linked user's full name simultaneously. An Export CSV button streams the currently filtered rows as UTF-8 CSV (ID, timestamp, subsystem, action, actor, role, IP, details); the export itself is audit-logged as audit_log_exported tagged SS6.
  • Configure System Settings — Whenever policy needs adjustment, the GM opens System Settings and edits session_timeout (5–1440 min), lockout_threshold (3–20), lockout_minutes (5–120), otp_expiry (5–60), penalty_grace_days (0–30), and default_penalty_rate (≥0). The System validates each value and persists every key into system_settings with the GM's id as updated_by, then audit-logs settings_updated.
  • Audit-Log Auth Events — Cross-cutting at every step, the System writes an AuditLog entry tagged source = SS6 for every auth/admin event: login, logout, failed_login, account_activated, password_change, settings_updated, and audit_log_exported — capturing actor, role, timestamp, IP, and details for traceability and BBT verification.
Subsystem 07

Communications & Notifications

Tenant-submitted requests & complaints, GM response with status workflow + Resolved lock, broadcast / direct announcements, the in-app notification bell, and bell + email fan-out for every comms event.

Use Case Diagram

Fig. 7.1 — Communications & Notifications use cases (Tenant Submissions, GM Comms Management, Tenant Notification Bell, System Automated bell + email).

Business Activity
  • Submit Maintenance Request — Communications begin tenant-side: the Tenant opens My Requests, picks type = request, fills subject (max 150) and body (max 2000), and submits. The System persists a TenantRequest with the tenant_id, then fans out a bell + email (TenantRequestMail) to every active GM, then shows the "Submitted" confirmation modal.
  • Submit Complaint — The same form with type = complaint. Validation, persistence, and GM bell + email fan-out are identical, and the modal label switches to "Complaint".
  • Notify GMs on New Tenant Request — Immediately on submit, the System writes one NotificationLog row of type tenant_request for every active GM and dispatches TenantRequestMail to each — bell + email in one fan-out.
  • View, Filter & Search Tenant Requests — Notified, the GM opens Tenant Requests (paginated 15/page, latest first). Dropdowns filter by status (Pending / In Progress / Resolved) and type (Request / Complaint); a search box matches subject or tenant full name.
  • Respond to Request & Update Status — The GM opens a request, types an admin reply (max 2000), and picks a new status (Pending / In Progress / Resolved). The System validates, persists admin_response + responded_by + responded_at, then fans out a tenant bell + RequestResponseMail. Resolved is final — once a request is saved as Resolved, the modal refuses further edits ("This request is already marked Resolved and can no longer be edited").
  • Notify Tenant on Request Response — Triggered by the response, the System writes a NotificationLog row of type request_response for the tenant and dispatches RequestResponseMail with the new status.
  • View Notification Bell — The Tenant (or any signed-in user) sees the bell with an unread badge counting their unread NotificationLog rows; opening the menu shows the 10 latest notifications.
  • Open Notification (marks read + redirects) — Clicking a notification entry calls NotificationBell::open(): the System marks the row is_read = true, then resolves a role-aware action URL via NotificationLog::actionUrl() and navigates to it (e.g., a tenant clicking a request_response goes to their request thread; a GM clicking tenant_request goes to the request viewer).
  • Mark All Read — The user clicks Mark all read and the System bulk-updates every unread NotificationLog row for that user to is_read = true, clearing the badge.
  • Compose & Send Announcement — Independently of the tenant-driven flow, the GM may broadcast: opening the announcement composer, entering title (max 150) and body (max 2000), and picking recipients — All active tenants or one specific tenant. The System validates (specific requires a valid user id), writes the Announcement row with email_sent = true, and per recipient writes a NotificationLog row + dispatches AnnouncementMail. The success flash reports the recipient count.
  • Notify Recipients on Announcement — Driven by the same send action, the System iterates the resolved recipients and per recipient writes a NotificationLog row of type announcement + dispatches AnnouncementMail.
  • View Announcement History — Afterwards the GM reviews every prior announcement (paginated 15/page, latest first) with sender, recipient (or "All"), and timestamp. A search box matches title or body.
  • Audit-Log Communications Events — Cross-cutting at every step, the System writes an AuditLog entry tagged source = SS7 for every comms event: tenant_request_submitted (tenant), tenant_request_responded (GM), and announcement_sent (GM) — capturing actor, role, timestamp, and a human-readable note for traceability and BBT verification.
