Citiescapes — System Flows Guide

This document describes every business flow in the Citiescapes Apartment Rental Management System, organised by subsystem and end-to-end scenario. It is the canonical "how the system actually works when you click a button" reference — read this alongside the use-case diagrams (use_cases_all_subsystems.html) and the event tables (EVENT_TABLES_REVISED.txt).

System overview

Citiescapes is a Laravel 11 + Livewire 3 + MySQL apartment rental platform. It is structured as seven subsystems (SS1 – SS7) that share one database and one authenticated session, but are kept logically isolated so each can be reasoned about, tested, and audited independently.

What the system manages

  • A fixed inventory of 22 rooms across 3 floors (compact / spacious).
  • Tenant accounts and their lease contracts.
  • Monthly billing, utility charges, penalties, and payments.
  • Public room listings + inquiries from prospective tenants.
  • An archive of every terminated, expired, deleted, or restored record.
  • An audit log of every state-changing action across all subsystems.

What the system does not manage

  • Physical building maintenance work-orders (it tracks requests, not work).
  • Legal eviction process — the software flags it, the GM acts in real life.
  • Tax accounting, bookkeeping, or formal financial reports.
  • Multi-property portfolios — one deployment = one building.

SS1 — Room Operations

Manages the physical inventory and the public-facing room-type cards.

What lives here

  • app/Livewire/Admin/Rooms/RoomManager.php — admin CRUD on rooms + the Public Room Type Cards editor.
  • app/Livewire/Admin/Rooms/InquiryManager.php — public-inquiry inbox.
  • app/Livewire/Public/RoomListings.php — the public website's room browser.

Flow A: GM updates a room

  1. GM Navigates to Room Management, clicks Edit on a room row.
  2. GM Adjusts rate, max occupants, description, amenities; saves.
  3. System Updates the row, writes room_updated to audit log (SS1).
  4. Public Next visit to the public listings shows the new data immediately.

Flow B: GM changes room status

  1. GM Clicks Status ▾ on a room row.
  2. System If the room has current_tenant_id set, the dropdown is locked. An occupied room stays occupied — maintenance happens in-place via a tenant request (SS7 Flow B), not by flipping the room's status.
  3. GM Picks Available / Occupied / Maintenance (only available when the room is empty).
  4. System Writes room_status_change to audit log with old→new.
Design note — why no Transfer Tenant action. An earlier draft of this system included a "Transfer Tenant" action that moved a tenant to another available room so the original could go on maintenance. That feature was removed because it broke at full occupancy (no destination room to move to) and added contract-state complexity for a scenario that's better served by in-place maintenance. The correct flow is: the tenant submits a request describing the issue (SS7), the GM coordinates the fix with the tenant in residence, the room status stays occupied the whole time. The maintenance work is tracked by the request's status (pending → in progress → resolved), not by the room's status field.

Flow C: GM edits Public Room Type Cards

These are the two cards (Compact / Spacious) shown on the public landing page. They live as a JSON blob in system_settings.room_type_cards.

  1. GM Clicks Edit Public Room Cards → modal opens.
  2. GM Edits title, subtitle, default price, max occupants, amenity chips, photos.
  3. GM To replace a photo, clicks Choose or Replace; file picker opens; tenant selects a JPG/PNG/WebP from disk.
  4. System Uploads via the patched Livewire upload route (app/Http/Controllers/PatchedLivewireUploadController.php) — fixes a Windows/Laragon realpath bug that breaks the default upload.
  5. System Stores the file under storage/app/public/room-type-cards/ and writes the URL into the JSON.
  6. GM Clicks Save Public Cards; room_cards_updated goes to audit log.

Flow D: Public visitor submits an inquiry

  1. Public Fills the inquiry form on the public room listing page.
  2. System Creates an inquiries row with status pending.
  3. System Notifies all active GMs via in-app bell + email.
  4. GM Opens Inquiry Log, clicks Email Reply, types a response.
  5. System Sends the email and flips the inquiry to responded. GM can later Close it.

Flow E: Archive Room (Clear Tenancy) CHANGED 2026-05-20

Clicking Archive on a room no longer removes the room from inventory. It now ends the current tenancy and resets the room to default available state, archiving the tenant + their contract along the way.

  1. GM On a room row, clicks the red-outlined Archive pill (with confirmation prompt — copy varies based on whether the room is occupied).
  2. System Always: snapshots the room's current state into archives (record_type = room, source_subsystem = SS1).
  3. System If a tenant was occupying the room:
    • Snapshots the tenant account into archives (record_type = tenant_account, source_subsystem = SS2), flips the user to archived with archived_at + archived_by stamped.
    • Finds the active contract bound to this tenant + room, sets it to terminated with a reason citing the room clear-out, snapshots it into archives (record_type = contract, source_subsystem = SS4, scan path preserved).
  4. System Resets the room row: current_tenant_id = null, status = available, last_status_update = now. The room itself stays in inventory with the same id, room_number, floor, type, rate, amenities — it is immediately editable and can be re-occupied.
  5. System Writes a single room_cleared audit-log entry summarising who was archived, contract id, and reason.
Why this changed. Previously, "Archive Room" soft-deleted the room itself — which conflated "tenant moved out" with "we're decommissioning this room". In a building with 22 fixed rooms, you essentially never want to soft-delete a room; you want to clean it up between tenants. The Permanently Delete Room button still exists for the rare case where a room actually leaves the inventory (e.g. renovation merged two rooms into one).

SS2 — Tenant Management

Creating tenant accounts, archiving them, and providing the tenant their first password.

Flow: GM creates a tenant account

  1. GM Tenant Management → + Create Tenant; enters full name + email.
  2. System Generates a random 10-character temp password, creates the user with role tenant, status pending_activation, and must_change_password = true.
  3. System Emails the temp password to the tenant (app/Mail/TempPasswordMail.php).
  4. Tenant Logs in, OTP is enforced, then is required to change password (SS6 takes over here).

Flow: GM archives a tenant

  1. GM Clicks Archive on a tenant row.
  2. System Creates an archives row of type tenant_account with reason "Tenant record archived by management", sets the user's status to archived.
  3. From the Archive page (SS5), the GM can Restore to bring the tenant back to active, or Delete Permanently.

SS3 — Billing & Collections

The most operationally important subsystem. Initial fees, monthly bills, payments, penalties, partial payments, and arrears handling.

Flow A: Recording the initial (move-in) payment

  1. GM Billing → Record Initial Fees.
  2. GM Picks a contract that's awaiting initial payment.
  3. System Auto-fills deposit + first month rent + key fee + amenity totals from the contract (SS4).
  4. GM Selects payment method (cash / bank transfer / e-wallet) + optional reference, submits.
  5. System Creates an initial_payments row, audit-logs initial_payment_recorded.
  6. Tenant Sees the receipt on their My Bills page.

Flow B: Generating a monthly bill

  1. GM Billing → Generate Monthly Bill.
  2. GM Picks a contract, enters electricity / water / wifi usage.
  3. System Creates a bills row with type = monthly, billing period = current month, due date = end of month, status unpaid.

Flow C: Confirming payment (full or partial)

  1. GM Clicks Confirm Pay on an unpaid bill, enters amount + method.
  2. System Creates a payments row.
  3. System Recomputes the bill's balance (Bill::balance accessor = total − sum of payments).
  4. System If balance ≤ 0: flips status to paid, stamps paid_at, logs payment_confirmed.
    If balance > 0: keeps existing status (eg. eviction), logs payment_partial with the new balance. NEW
Partial-payment design note. Before the fix, the system flipped the bill to paid regardless of amount — so a tenant in arrears could pay ₱100 of a ₱8 000 bill and the system would mark it settled. Now, the bill remains in its prior status until the cumulative payments cover total_amount. This matters most in delinquent / eviction states where multiple partials are common.

Flow D: Daily penalty cascade (automated)

Runs once per day via the Laravel scheduler.

  1. System app/Console/Commands/ApplyBillingPenalties.php sweeps every unpaid bill.
  2. System For each bill, computes days_overdue from due_date and steps the status:
    • 0 days: unpaid
    • 1–3 days: grace (grace period, no penalty yet)
    • 4–14 days: overdue (penalty ₱100/day starts accruing)
    • 15–29 days: delinquent
    • 30+ days: eviction
  3. System Adds the day's penalty to penalty_amount, updates total_amount.

Flow E: GM overrides a penalty

  1. GM Clicks Override on a bill with a penalty.
  2. GM Enters an adjusted penalty amount + written reason; saves.
  3. System Creates a penalty_overrides row, updates the bill's penalty + total. Audit-logs penalty_override.

Flow F: Apply Deposit to Arrears NEW

  1. GM On a bill in delinquent or eviction, clicks Apply Deposit.
  2. System Computes remaining deposit = contract.deposit − contract.deposit_applied_amount.
  3. System Applies the smaller of (remaining deposit) or (bill balance), creates a payments row tagged deposit_applied, increments deposit_applied_amount, stamps deposit_applied_at.
  4. System If this clears the balance, flips the bill to paid. Audit-logs deposit_applied_to_bill.

Flow G: Mark for Termination (eviction shortcut) NEW

  1. GM On a bill in delinquent or eviction, clicks Mark for Termination.
  2. System Auto-fills a termination reason citing the bill, flips contract to terminated, archives the contract (SS5), archives the tenant, frees the room. Audit-logs contract_terminated_arrears.

SS4 — Contract & Lease Management

The legal binding between a tenant and a room. Drafts → activation → expiry → archive.

Flow A: GM creates a contract draft

  1. GM Contract Management → + Create Draft.
  2. GM Picks tenant + room (rent auto-fills from room's rate), sets deposit, key fee, start/end dates, penalty rate, grace days, house rules.
  3. GM Optionally adds requested amenities (one-time fees billed at move-in).
  4. GM Uploads a scan of the signed contract (PDF / JPG / PNG / WebP / DOC / DOCX, max 10 MB).
  5. System Saves contract with status draft.

Flow B: Tenant acknowledges the contract (2 steps)

  1. Tenant Opens My Contract.
  2. Tenant Step 1: clicks "I have read and understood this contract" — stamps step1_acknowledged_at.
  3. Tenant Step 2: clicks "I accept the penalty clause" — stamps step2_acknowledged_at, flips contract to active, stamps activated_at, links room to tenant.
  4. System Audit-logs contract_step1_ack and contract_step2_ack.

Flow C: GM activates a contract directly

Used when the tenant signs in-person and the GM wants to skip the portal-side acknowledgment.

  1. GM Clicks Activate on a draft contract.
  2. System Guards:
    • Refuses if contract is not draft.
    • Refuses if the linked room is already occupied by another tenant.
    • Refuses if the signed contract scan has not been uploaded — the paper IS the legal document, so the GM must upload it before going live (NEW guard).
  3. System Flips contract to active, marks the room occupied with current_tenant_id, promotes the tenant from pending_activation to active.
  4. System NEW Auto-stamps step1_acknowledged_at and step2_acknowledged_at with the activation timestamp if they're empty. Path B happens when the tenant signed paper in person — the paper IS the agreement, so the digital acknowledgment fields are mirrored to keep the database state consistent. The audit-log entry distinguishes "GM-initiated activation (paper signed)" from "GM-initiated activation after tenant in-portal acknowledgment", so a future reader can tell which path was used.

Flow D: Contract scan view approval NEW

For security, tenants cannot view the signed contract scan without explicit GM approval.

  1. Tenant Opens My Contract, sees the scan area locked with a "Request access" button.
  2. Tenant Clicks Request access; contract's scan_view_status becomes pending.
  3. GM Sees a "Tenant requested access" badge on the Contracts page. Clicks Approve or Deny (deny requires a reason).
  4. System Stamps scan_view_decided_at, scan_view_decided_by.
  5. Tenant Refreshes My Contract:
    • Approved → scan loads inline (PDF in iframe, image inline, .doc/.docx as a download button).
    • Denied → sees reason + "Request again" button.
  6. GM can later Revoke, returning the contract to no-access state.

Flow E: Renewal

  1. GM Clicks Renew on an active contract.
  2. System Archives the old contract to SS5 with reason "Renewed — old contract archived", flips its status to expired.
  3. System Pre-fills a new draft with the same tenant, room, terms, but start date = day after old end date.
  4. GM Reviews the draft, makes any changes (e.g., rate increase), saves. Then activates as in Flow C.

Flow F: Termination (early end)

  1. GM Clicks Terminate on an active contract, enters reason.
  2. System Flips contract to terminated, archives to SS5, archives the tenant, frees the room.

Flow G: Auto-archive on expiry (automated)

  1. System app/Console/Commands/AutoArchiveExpiredContracts.php runs daily.
  2. System For every contract where end_date < today and status is still active, archives it with reason "Auto-archived — lease end date passed" and flips it to expired.

Flow H: Lease-expiry warnings (automated)

  1. System Daily, for every active contract 30 days from end_date (one-time), sends a warning email + bell to the tenant and flips warning_30_sent = true.
  2. System Same for the 7-day mark with warning_7_sent.

SS5 — Report and Archive Management

Every other subsystem pushes records here when something gets terminated, expired, or removed. SS5 is read-only at the row level — modifications happen at the source subsystem.

Flow A: Browsing the archive

  1. GM Archive. Filters by Type (room / tenant / payment / contract) and Source (SS1–SS4). Date-range filter available.
  2. GM Universal search across reason, type, source, date.

Flow B: Export

  • Export CSV — streams a UTF-8 CSV of the filtered list. Audit-logged.
  • PDF button (per archived contract) — generates a printable PDF (resources/views/pdf/archived-contract.blade.php) with all contract fields + a reference to the stored scan.

Flow C: Restore (tenant accounts only)

  1. GM On a tenant_account archive row, clicks Restore (the button is shown only for that record type).
  2. System Re-activates the user — status back to active, clears archived_at / archived_by — so the tenant can log in again. Marks the archive row restored = true with restored_at. Audit-logs record_restored.
Why restore is tenant-only. A tenant account is the one archive type where restoration is both impactful (a person regains access) and safe (just a status flip). Room archives are snapshots — the room itself was never deleted, so there's nothing to restore. Contract and payment archives are immutable historical records: un-terminating a contract or reviving a settled bill would collide with room occupancy and the penalty scheduler. Those rows have no Restore button and the controller rejects any attempt server-side. To revive a contract scenario, the GM creates a fresh draft (SS4) pre-filled from the archived data — which goes through the normal activation guards.

Flow D: Permanent delete

  1. GM Clicks Delete Permanently (red, confirmation prompt).
  2. System Hard-deletes the archive row. Audit-log retains the action via record_permanently_deleted.

SS6 — User Access & Authentication

Flow A: First-time login (tenant)

  1. Tenant Receives temp password via email (from SS2 Create Tenant flow).
  2. Tenant Logs in on the public login page using email + temp password.
  3. System Validates credentials, sends a 6-digit OTP to the tenant's email.
  4. Tenant Enters OTP on the verification page.
  5. System Because must_change_password = true, redirects to the Change Password page.
  6. Tenant Sets a new password.
  7. System Clears must_change_password, lands the tenant on the dashboard. Audit-logs password_changed.

Flow B: Lockout protection

  1. System After 5 failed login attempts within 15 minutes, locks the account.
  2. System Lock auto-clears after 15 minutes; the user can also reset by clicking "Forgot password".
  3. System All failed attempts and lockouts go to the audit log.

SS7 — Communications & Notifications

Flow A: GM sends an announcement

  1. GM Announcements → New Announcement; types title + message, picks "All Active Tenants" or one specific tenant.
  2. System Creates an announcements row. For each recipient: creates a notification_logs row (in-app bell) and sends an AnnouncementMail.

Flow B: Tenant submits a request or complaint

  1. Tenant My Requests → New; picks type (request / complaint), subject, body.
  2. System Creates a tenant_requests row with status pending. Notifies all active GMs (bell + email).
  3. GM Tenant Requests, opens the row, updates status (pending → in progress → resolved), writes a response.
  4. System Sends response to tenant (bell + email). Once status is resolved, the request locks — no further edits.

Flow C: Payment-plan request NEW

A specialised version of Flow B, triggered from the tenant billing page.

  1. Tenant Has a bill in delinquent or eviction; sees red banner on My Bills.
  2. Tenant Clicks Request payment plan.
  3. System Guards against duplicates (one open request per bill).
  4. System Creates a tenant_requests row with auto-filled subject "Payment difficulty — Bill #N (period)" and a body summarising the balance.
  5. System Notifies all GMs (bell + email). Audit-logs payment_plan_requested under SS3.
  6. GM Handles the request via SS7 Flow B's response interface, then takes action in SS3 (Override Penalty, Apply Deposit, or Confirm a partial payment).

End-to-end: New tenant move-in

Crosses SS2 → SS4 → SS6 → SS3. Time horizon: a few hours of clicking, then 24 hours for tenant to acknowledge.
  1. GM SS2: Creates tenant account → temp password email sent.
  2. Tenant SS6: Logs in with temp password → OTP → sets new password.
  3. GM SS4: Creates contract draft with tenant + chosen room, uploads signed scan.
  4. Tenant SS4: My Contract page → Step 1 ack → Step 2 ack → contract auto-activates, room becomes occupied.
  5. GM SS3: Records initial payment (deposit + first month + key fee + any amenities).
  6. Tenant SS3: Sees the initial payment receipt on My Bills page.

End-to-end: Monthly billing cycle

  1. GM SS3: Generate Monthly Bill for the contract, entering utility usage.
  2. Tenant SS3: Sees the new bill (status unpaid) with breakdown.
  3. Tenant Pays the GM via the agreed method (cash / bank / e-wallet — outside the system).
  4. GM SS3: Clicks Confirm Pay, enters amount + reference.
  5. System Flips bill to paid if balance reached zero, otherwise keeps status and logs partial.
  6. System If the due date passes without full payment, the daily scheduler advances the status through grace → overdue → delinquent → eviction, accruing penalty each day past grace.

End-to-end: Lease renewal

  1. System Sends 30-day and 7-day warnings to the tenant.
  2. GM SS4: Clicks Renew → old contract archived, new draft pre-filled with continuing dates.
  3. GM Adjusts rate / amenities / scan if needed, uploads new signed scan, saves.
  4. Tenant SS4: My Contract page now shows new draft → does Step 1 + Step 2 acknowledgment.
  5. GM SS3: Records new initial payment if deposit/keys changed.

End-to-end: Arrears & eviction NEW

Crosses SS3 → SS7 → SS4 → SS5. The most sensitive flow in the system; every step is audit-logged.
  1. System SS3 daily scheduler: bill misses due date → status advances over days from grace → overdue → delinquent → eviction. Penalty accrues from day 4.
  2. Tenant SS3: Sees red banner on My Bills page once status hits delinquent or eviction.
  3. Tenant Has three real-world options:
    • Pay in full — pays GM, GM clicks Confirm Pay, bill closes.
    • Partial pay + plan — pays what they can, then clicks Request payment plan (SS7 Flow C).
    • Surrender — agrees to leave, GM applies deposit and terminates.
  4. GM Reviews the request in SS7, decides.
  5. GM Possible SS3 actions:
    • Override the penalty (lower it as a concession).
    • Apply Deposit as a credit against the bill.
    • Accept a partial payment — bill stays open until balance reaches zero.
    • Mark for Termination if the tenant won't or can't pay.
  6. System If Mark for Termination is used: contract → terminated, archived to SS5, tenant → archived, room → available. The cycle ends.

End-to-end: Room needs maintenance while tenant is occupying it

Crosses SS7 → SS1. Tenant stays in the room; the work happens with them in residence. The contract is untouched and no rooms change occupancy.
  1. Tenant Notices a problem (leak, broken AC, electrical issue, etc.) and submits a Tenant Request via My Requests → New (SS7 Flow B). Type: request. Subject and body describe the issue.
  2. System Creates a tenant_requests row, status pending. Notifies all active GMs (bell + email).
  3. GM Opens Tenant Requests, reviews the issue, updates status to in_progress, writes initial notes (e.g. "Maintenance scheduled for Friday morning").
  4. System Sends the GM's response to the tenant via bell + email.
  5. GM Coordinates the repair: contacts contractor, schedules access, ensures tenant is available or has agreed to entry.
  6. (Maintenance happens in real life. The room stays occupied the whole time; the room's status is not changed.)
  7. GM Once verified the issue is resolved, updates the request to resolved with a final response (e.g. "Plumber replaced the valve, water restored, no further work needed.").
  8. System Locks the request from further edits and sends the final response to the tenant. The audit log retains the full timeline (tenant_request_submitted, tenant_request_status_change, etc.).
Edge case — uninhabitable room. If the room becomes genuinely uninhabitable (fire, structural failure, prolonged loss of water/power) and there is no available room to move the tenant to, the GM should use SS4 Flow F (Terminate) with a reason like "Room declared uninhabitable — early termination at GM discretion". The tenant has legal grounds to break the lease in this case; refunds and re-housing happen outside the system.

End-to-end: Tenant requests scan access NEW

  1. Tenant SS4 My Contract: scan viewer is locked with an "Approval required" message.
  2. Tenant Clicks Request access.
  3. System Sets scan_view_status = pending, stamps scan_view_requested_at.
  4. GM SS4 Contracts page: sees the "Tenant requested access" badge. Clicks Approve or Deny.
  5. System Records the decision, who decided, optional note.
  6. Tenant Refreshes: sees the scan inline (if approved) or the denial reason + "Request again" button (if denied).

Automation (schedulers)

The following Artisan commands are wired into the Laravel scheduler. They are the system's only "fully automatic" actors.

CommandScheduleEffect
billing:apply-penalties Daily Advances every unpaid bill's status by days overdue and accrues penalty (SS3 Flow D).
contracts:auto-archive Daily Expires + archives contracts past their end_date (SS4 Flow G).
contracts:send-warnings Daily Sends 30-day and 7-day lease-expiry warnings (SS4 Flow H).
room:sync-status Hourly Reconciles rooms.status with the actual presence of an active contract (defensive — catches drift).

Recent additions (changelog)

Changes since the system's CS12L baseline, ordered most-recent first.

2026-05-19 — Maintenance design decision (no Transfer Tenant)

  • An earlier draft added a "Transfer Tenant" action that moved an occupying tenant to another available room so the original could go on maintenance. It was removed.
  • Why removed: the feature broke at full occupancy (no destination room), added contract-state complexity, and duplicated work the existing tenant-request workflow already handles.
  • Correct flow: tenant submits a Tenant Request (SS7), GM coordinates the fix in-place, room stays occupied the whole time. The request's status (pending → in progress → resolved) is the source of truth for the maintenance work.
  • Edge case: if the room becomes uninhabitable, GM uses SS4 Terminate with reason "Room declared uninhabitable" — refunds happen outside the system.

2026-05-19 — Eviction & arrears flow

  • Partial-payment aware confirmPayment — bills only flip to paid when the balance reaches zero.
  • New tenant action: Request payment plan from a red banner on My Bills (SS7 Flow C).
  • New GM action: Apply Deposit to Arrears (SS3 Flow F).
  • New GM action: Mark for Termination shortcut from a bill (SS3 Flow G).
  • Schema: contracts.deposit_applied_amount + deposit_applied_at.

2026-05-19 — UI/UX standardisation

  • All modals normalised to a single .cs-modal CSS class with full-viewport dim + clearance below the sticky header.
  • Filter dropdowns across every admin page replaced with horizontal rectangular brand-button bars (rounded-lg, active=filled, inactive=outlined).
  • All search inputs match across every visible column on their page, not just one or two fields.
  • Sidebar scrollbar restyled to brand colours, slim 8 px.
  • Page-enter animation moved to main > * and is opacity-only so main never becomes a containing block for fixed-positioned modals.

2026-05-19 — Contract scan access approval

  • Tenants must request GM approval before viewing the signed contract scan (SS4 Flow D).
  • Schema: contracts.scan_view_status, scan_view_requested_at, scan_view_decided_at, scan_view_decided_by, scan_view_decision_note.
  • Scan upload widened to accept .doc and .docx (10 MB cap); .docx renders as a download button on the tenant side.

2026-05-20 — Final compiled revision

  • Restore restricted to tenant accounts. The Restore button now appears only on tenant_account archive rows; room/contract/payment archives are immutable snapshots. The controller rejects any restore attempt on a non-tenant type.
  • Empty-data export guards. Archive CSV and Audit-Log CSV exports now refuse to run when the filtered result set is empty — a flash error is shown instead of streaming a header-only file. No audit row is written for a refused export.
  • System-wide validation hardening. Every create/update/action form has explicit required-field rules with human-readable messages, inline @error displays, red-ring error states, and loading states on submit buttons.
  • Cross-database dashboard query. The revenue-by-month chart no longer uses the MySQL-only DATE_FORMAT — it groups in PHP, so the dashboard renders on both MySQL (production) and SQLite (tests).
  • Test suite: 273 passing, 0 failing, 0 pending. All BBT + WBT cases updated to match the finalized behavior.

2026-05-20 — Archive Room behavior changed (SS1 Flow E)

  • Behavior change: "Archive" on a room used to soft-delete the room. It now ends the current tenancy and resets the room to available, keeping the room in inventory.
  • The room snapshot, the tenant account, and the active contract all get archived (record_type = room / tenant_account / contract).
  • The room itself stays — same id, room number, floor, rate, amenities — immediately editable and ready to be re-occupied.

Gotchas & conventions

  • Soft-delete vs archive vs hard-delete. Contracts and bills use Laravel soft-deletes for accidental-undo. The archive action does a different thing — it copies a snapshot into archives for historical reference. "Permanently delete" from the Archive page is the only operation that truly removes data.
  • Audit log is append-only. Every state-changing controller action writes one row to audit_logs. Never edit or delete these rows — they are the system's compliance record. Filter is by Subsystem (Room / Tenant / Billing / Contract / Archive / Settings / Communications), not raw "SS1" codes.
  • The GM is one person. The role is named "General Manager" but the system makes no distinction between multiple GM accounts. Notifications fan out to "all active GMs" wherever applicable.
  • "System" in audit log = scheduler. Any audit_logs row with user_id = null was written by an automated command, not a person.
  • Public site re-renders live. The public room listings page reads from system_settings.room_type_cards on every request. There is no static cache to invalidate — saving the cards editor is immediately visible to visitors.
  • Auto-archive vs Terminate. Auto-archive is for the natural end of a lease (it ran its course). Terminate is for early end (tenant left, eviction, mutual cancellation). They use the same archive sink but capture different reasons.
  • Partial payments and eviction. A tenant in eviction can still make payments — the bill stays in eviction status until the balance reaches zero. The GM has to decide whether the partial restores their good standing (none of the auto-status code reverses on its own; the next daily scheduler tick will just check overdue again).
