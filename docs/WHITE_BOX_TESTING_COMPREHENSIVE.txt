1. INTRODUCTION TO WHITE-BOX TESTING
================================================================================

DEFINITION:
  White-box testing (structural testing, glass-box testing) examines the
  INTERNAL LOGIC of code. The tester knows the source code and designs test
  cases that exercise specific statements, branches, and paths.

  The term "white-box" comes from the idea that the internal logic is visible
  and transparent, unlike the hidden internals of black-box testing.

PURPOSE:
  - Validate internal logic paths execute correctly
  - Test decision branches (if/else/switch)
  - Verify loop execution
  - Find code-level bugs
  - Achieve high code coverage
  - Test error handling paths

ADVANTAGES:
  ✓ Finds code-level bugs
  ✓ Tests all execution paths
  ✓ Can test error handling
  ✓ Identifies untested code
  ✓ Ensures complete branch coverage
  ✓ Detects unreachable code

DISADVANTAGES:
  ✗ Requires code knowledge
  ✗ Time-consuming to write tests
  ✗ Tests implementation, not specification
  ✗ Cannot test user experience
  ✗ May miss business logic errors

WHEN TO USE:
  - Testing internal logic and calculations
  - Ensuring all branches execute
  - Verifying error handling
  - After black-box testing
  - For critical modules
  - In code review process

DIFFERENCE FROM BLACK-BOX:

  Black-Box (User Perspective):
    ✓ Tests "what the system does"
    ✓ Tests user-facing features
    ✓ Focuses on functionality
    ✓ No code knowledge needed

  White-Box (Developer Perspective):
    ✓ Tests "how the system works"
    ✓ Tests internal logic
    ✓ Focuses on implementation
    ✓ Requires code knowledge

  Ideal Testing: Use BOTH together for complete coverage

2. BRANCH COVERAGE TECHNIQUE
================================================================================

CONCEPT - WHAT IS A BRANCH?

  A "branch" is one of two or more execution paths through code created by
  a decision point (conditional logic).

  Decision Points:
    - if statement: 2 paths (true or false)
    - if/else: 2 paths (if branch or else branch)
    - if/elseif/else: 3+ paths (one per condition or else)
    - switch statement: N paths (one per case)
    - ternary (?:): 2 paths (true or false)
    - Logical && or ||: 2 paths (short-circuit or continue)

  BRANCH COVERAGE = All branches must be executed at least once

IDENTIFYING BRANCHES:

  Step 1: Find All Decision Points
  ---------------------------------
  Read through source code and identify every:
    - if / elseif / else
    - switch / case
    - ternary ? :
    - &&, ||, !
    - loops (while, for)

  Example Code:
    ```php
    if ($daysOverdue <= 3) {          // DECISION POINT 1
        // Grace period
        if ($daysOverdue === 1 || $daysOverdue === 3) {  // DECISION POINT 2
            sendGraceReminder();
        }
    } elseif ($daysOverdue < 14) {    // DECISION POINT 3
        // Overdue
    } else {                           // DECISION POINT 4
        // Delinquent
    }
    ```

  Step 2: Number Each Branch Outcome
  -----------------------------------
  Label decisions and their outcomes:

    Decision 1 ($daysOverdue <= 3):
      B1 = true (1-3 days overdue)
      B1F = false (4+ days overdue)

    Decision 2 ($daysOverdue === 1 || === 3):
      B1a = true (day 1 or 3)
      B1aF = false (day 2)

    Decision 3 ($daysOverdue < 14):
      B2 = true (4-13 days overdue)
      B2F = false (14+ days overdue)

    Decision 4 (else):
      B3 = true (automatically true if B2 false)

  Step 3: Create Test for Each Branch
  ------------------------------------
  For every branch outcome, design a test that forces execution:

    Test 1 (B1 = true): Input daysOverdue = 1
    Test 2 (B1 = false): Input daysOverdue = 14
    Test 3 (B1a = true): Input daysOverdue = 1 (also covers B1a = true)
    Test 4 (B1a = false): Input daysOverdue = 2
    Test 5 (B2 = true): Input daysOverdue = 10
    Test 6 (B3 = true): Input daysOverdue = 30

COMPLETE BRANCH COVERAGE:

  100% Branch Coverage Means:
    ✓ Every if/else branch executed at least once
    ✓ Every switch case executed at least once
    ✓ Every ternary branch executed
    ✓ Every loop executed AND skipped (for edge cases)
    ✓ All error paths tested

  Example Achievement:
    Original code has 5 decision points = 8 possible branches
    Write 8 tests, one for each branch outcome
    Run all tests and measure coverage
    Result: 100% branch coverage achieved

TESTING BOTH BRANCHES:

  CRITICAL: Test both TRUE and FALSE outcomes

  ✗ WRONG (Only tests true branch):
    if ($user->isAdmin()) {
        $user->deleteAccount();  // Only test this
    }

  ✓ CORRECT (Tests both branches):
    Test 1: isAdmin() = true → deleteAccount() executes
    Test 2: isAdmin() = false → deleteAccount() does NOT execute

BOUNDARY CONDITIONS IN BRANCHES:

  At Boundaries, Test:
    - Just before boundary (branch false)
    - Exactly at boundary (may switch branch)
    - Just after boundary (branch true)

  Example - Days Overdue <= 3:
    Test 1: days = 3 (at boundary, branch true)
    Test 2: days = 4 (just after, branch false)

NESTED BRANCHES:

  When branches contain other branches, test all combinations:

  ```php
  if ($user->isLocked()) {           // B1
      if (now() > $lockExpiry) {     // B1a
          $user->unlock();
      } else {
          denyLogin();
      }
  } else {
      allowLogin();
  }
  ```

  Test Cases Needed:
    1. B1 = false → allowLogin()
    2. B1 = true, B1a = true → unlock()
    3. B1 = true, B1a = false → denyLogin()

  Total: 3 tests for 2 nested decisions (not 4 or 5)

3. PLANNING METHODOLOGY
================================================================================

STEP-BY-STEP PROCESS:

STEP 1: SELECT MODULE TO TEST
  Pick one method/function (unit) to test
  Example: ApplyBillingPenalties::handle()
  File: app/Console/Commands/ApplyBillingPenalties.php

STEP 2: READ SOURCE CODE
  Analyze the method/function:
  - What inputs does it accept?
  - What logic does it contain?
  - What decisions are made?
  - What outputs does it produce?
  - What side effects does it have?

STEP 3: IDENTIFY ALL BRANCHES
  Find every decision point and number them:
    B1: if (daysOverdue <= 3)
    B1a: if (daysOverdue === 1 || daysOverdue === 3)
    B2: elseif (daysOverdue < 14)
    B3: elseif (daysOverdue < 30)
    B4: else

STEP 4: DESIGN TEST INPUTS
  For each branch outcome, design minimum input to execute it:

    B1 true: daysOverdue = 1, 2, or 3
    B1 false: daysOverdue = 4+
    B1a true: daysOverdue = 1 or 3
    B1a false: daysOverdue = 2
    etc.

STEP 5: CREATE TEST CASES
  Document each test with:
    - Test ID
    - Branch(es) covered
    - Input/Preconditions
    - Expected output
    - Actual output (filled during testing)
    - Pass/Fail status

STEP 6: EXECUTE TESTS
  - Run each test via PHPUnit
  - Capture coverage metrics
  - Verify each branch executed

STEP 7: VERIFY COVERAGE
  - Check coverage report
  - Identify untested branches
  - Add tests for gaps
  - Achieve 100% branch coverage
